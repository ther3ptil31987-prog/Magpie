# 0.6.10 Beta1：VRR 请求完整但无 G-SYNC 指示器的焦点诊断

日期：2026-10-04（Asia/Shanghai）。本轮只读检查运行日志、包清单和对应源码；仅更新功能分支文档，没有编译、部署、注入、切换真实焦点或修改驱动设置。

当前判断：**输出窗口的前台身份是首要待验证原因。标准 DXGI 请求接线已得到运行日志支持，但没有焦点 A/B 或实际 PresentMode 记录，不能认定焦点是唯一根因。**

## 复现与版本

用户确认测试 `0.6.10-beta1`，单屏输出、无补帧，NVIDIA 控制面板已启用“窗口和全屏模式”的 G-SYNC；启用 Magpie VRR 后没有出现 G-SYNC 指示器。

检查工作区 `release/v0.6.10-beta1/Magpie-Experimental-x64/build-manifest.json`：版本 `0.6.10-beta1`，源码 `e6b82596ec0161e7497462930001c36686b1f578`，`sourceDirty=false`。对应发布工作树通过 `24f08d2f` 合入 `1d6642ef` 的标准 VRR 接入，包含更新的 UWP 窗口协调；不是只查看尚未部署的功能分支源码。

本机包日志 `logs/magpie.log` 截至 17:51:31，五次终态初始化记录为：

| 17:45:52.129 | `0x310a0` | requested=true、eligible=true、creationFlags=0x840、presentFlags=0x200、reason=none |
| 17:50:47.928 | `0x350cf0` | 同上 |
| 17:50:57.846 | `0x361000` | 同上 |
| 17:51:04.367 | `0x250b50` | 同上 |

日志同时记录 NVIDIA RTX 5070 Ti、输出矩形 `2560×1440`、刷新间隔 `3.333 ms`（名义约 300 Hz），Front Edge 基础目标 60 FPS。最后一段来源类名为 `PotPlayer64`，使用 DLSSNR；这不是 DLSS／XeSS 补帧。

`0x840` 包含交换链 tearing 能力 `0x800` 和容量 waitable object `0x40`；`0x200` 是 Present tearing flag，SyncInterval 为 0。对应 `PresenterBase::_PresentWithVRR` 将该策略值传入交换链 Present。检查日志未发现后续创建／Present 拒绝或资格回退；首帧已提交并显示输出窗口。

这些事实支持“标准请求没有漏接线”。初始化日志不是逐帧 ETW 记录，基础目标也不是全部内容／光标／界面 Present 的实测速率；仍不能证明 Independent Flip、实际显示间隔或物理变频。

初始化前的五组 `reason=non-DXGI-path` 与 `reason=alt-enter-guard-failed` 是当前实现先探测、后标记 DXGI 路径、最后设置 Alt+Enter guard 的中间状态。每组均随后达到终态 `eligible=true reason=none`，不能把这些早期标签解释成本次最终回退原因。后续应显式区分初始化待完成与真正失败。

## 焦点行为的源码证据

以 `e6b82596` 的实际发布源码为准：

- `ScalingWindow.cpp:390`：全屏输出创建为 `WS_EX_LAYERED | WS_EX_NOACTIVATE | WS_EX_NOREDIRECTIONBITMAP`。
- `ScalingWindow.cpp:1206`：`WM_MOUSEACTIVATE` 返回 `MA_NOACTIVATE`。
- `ScalingWindow.cpp:1924`：普通会话如果真实前台变成输出 HWND，会调用 `_srcTracker.SetFocus()`，随后重新读取真实前台；参数输入的既有例外保留。
- `SrcTracker::SetFocus()` 最终调用 `SetForegroundWindow`，目标为源窗口或其活动 popup。
- `ScalingWindow.cpp:2574`：置顶使用 `SWP_NO_ACTIVATE_MOVE_SIZE`。置顶与前台身份独立，重复置顶不能代替焦点实验。
- `ExclModeHelper` 仅持有 `__DDrawExclMode__` 通知状态 mutex；“模拟独占全屏成功”不表示创建了 DXGI 独占全屏或获得前台。

标准 VRR 开关没有改变以上行为。当前设计保留源应用真实前台，而最终绘制／Present 属于 Magpie 的输出窗口。这一结构是 NVIDIA 窗口选择问题的候选触发条件，并非 Microsoft 标准 tearing 合同缺失。

本轮另做了一次 Win32 只读窗口元数据查询：采样时没有存活的 Magpie 缩放输出，前台是其他应用。因此没有获得“正在呈现时真实前台是谁”的同步样本，也没有执行真实焦点对照。

## NoFocusLoss 线索的边界

复核固定版本 `4d30610d89a9a279aa0ef9bcfb222994e381b663`：工具通过 MinHook 改写目标进程的 `GetForegroundWindow` 返回值，另有失焦消息和 `SetCursorPos` 处理；没有真实激活／置顶或 G-SYNC API。

若它注入 Magpie 且改变了指示器，可能影响同进程驱动／DXGI 看到的前台身份，也可能是消息处理或其他条件的结果。原反馈未确认注入目标，不能把“Magpie 驱动线程确实调用了这个 API”写成已证实机制。只改 Magpie 自己的 C++ 查询包装，不会自动改变驱动模块的查询。

NVIDIA 开发者论坛的 2024 年原始反馈描述了非前台全屏覆盖窗口无法触发 G-SYNC 的相似现象。它是旁证，没有公开保证现行驱动对所有非前台窗口都作同一判断。Microsoft／NVIDIA 的公开设置文档没有给出可直接调用的“无焦点窗口强制 G-SYNC”合同。

## 下一步应回答的问题

1. **先记录活动呈现状态**：启动后／首帧后／稳定期间记录真实前台 HWND 与 PID、源／输出 HWND、owner、style、路径、flags；从参数窗口恢复后再次记录。采集 PresentMon 实际显示事件，区分合成 Flip 与 Independent Flip／MPO，并固定外部叠加层条件。
2. **增加短时真实前台参考组**：在同一静态场景或持续动画、同一交换链／flags／尺寸／帧率下，诊断版本暂时允许输出持续持有真实前台，暂停其自动还焦点规则；保持其他窗口顺序条件一致，记录源捕获与 PresentMode 是否也改变，结束后恢复。直接用外部工具激活当前版本会被自动纠正规则撤销，不能算有效 B 组。
3. **分离进程内查询伪装与消息处理**：在不更改 Windows 真实前台的前提下，先采集查询的调用来源；确认驱动确实消费该入口后，再分别运行 TODO 中 B／C／D 组。Magpie 自己的源状态、WGC、参数／IME、快捷键继续走真实查询通道，默认不拦截光标 API。
4. 每组同步记录 NVIDIA 指示器、显示器实时 Hz／LFC 和最终显示间隔。真实前台组独自触发时支持焦点相关选择；若同时 PresentMode 改变，仍需区分其贡献。只有查询伪装组有效时，才支持该进程内入口可用于兼容实现；所有组都失败时，继续检查 Magpie 程序配置、显示器／驱动启用状态、呈现路径和其他覆盖窗口。

真实前台参考组只用于短时诊断，不作为发布默认策略。游戏可能在失焦后暂停、后台限帧或丢失键鼠输入；因此实际兼容目标仍是源应用保持真实前台，驱动选择最终 Magpie 输出。当前没有实现或运行此参考组，也没有新增产品 Hook。
