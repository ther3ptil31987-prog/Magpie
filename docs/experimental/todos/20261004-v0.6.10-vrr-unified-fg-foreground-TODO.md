## 2. Beta2 问题与修正依据

### 2.1 FG 统一拒绝条件是直接阻断点

部署源码 `NvidiaForegroundCompatibility.cpp:190–194` 的 `Publish()` 中，资格要求含 `!control.frameGeneration`。`DeviceInitialized()` 把任何 FG 链记录为 `fg-outside-prototype`；`PresentationState()` 的状态原因更新也带有同一排除条件。`Renderer.cpp:373` 在效果链存在 FG 时设置 `_hasFrameGeneration`，并于 `:424` 传入该控制器，覆盖 DLSS 与 XeSS 两条路径。

日志证据来自包内 `logs/magpie.1.log`，时间及行号以本轮读取快照为准：

- `:425–431`，23:04:22，epoch=5：源实际前台 `0x51088`、`sourceForeground=true`，`requested=true installed=true`，但 `armed=false appliedQueries=0 targetQueries=95597 reason=fg-outside-prototype`。查询入口已命中，覆盖被共同 FG 条件关闭。
- 同一 FG 会话的输出环记录约 60 FPS 捕获、240 FPS 入队，生成帧与真实帧持续发布。这次失败应先处理资格阻断，随后按最终输出检查节奏。
- `:1169–1171`，23:05:46，epoch=6：`nvwgf2umx.dll` 的首次 / 稳定查询由真实源 `0x51088` 返回输出 `0x11160`。此前“是否存在实际驱动查询”的问题已获得本机命中记录。
- `:2487–2489`，23:18:11，epoch=12：同一驱动模块由源 `0x240eae` 返回输出 `0xd10ac`；随后 `magpie.log:2–19` 的 appliedQueries 持续增加，直到正常退休。

**修正方向：按最终 presenter 的实际能力判定资格，解除“效果链带 FG 即关闭”的总开关。** 同时修改资格、原因记录和诊断参考模式，保持实际 HWND、交换链合同与会话寿命一致。

### 2.2 两个用户开关控制同一完整功能

标准层控制创建 / Resize / Present 的 tearing 合同；NVIDIA 层补足源游戏持有前台时的呈现窗口身份。用户正常使用需要二者同时存在，独立开关产生了三个不完整组合。

**修正方向：保留分层实现，界面和配置意图收敛成一个 VRR 开关。** 开启后标准层正常运行，NVIDIA 输出自动派生前台兼容；其他厂商走标准路径。诊断的标准单独 / Trace / Reference 比较继续通过开发入口进行。

### 2.3 鼠标进入源画面是现有输入路径，呈现侧关联需要保持

`CursorManager.cpp:560–563` 在 3D 游戏模式中把缩放窗口设为鼠标透明；普通模式捕获光标时也会设置 `WS_EX_TRANSPARENT`。`ScalingWindow.cpp:1221–1224` 返回 `MA_NOACTIVATE`，`:1943–1949` 在输出意外激活时恢复源焦点。这些动作让源游戏正常接收输入。

前台返回替换只发生在 Magpie 进程内的目标调用；捕获、输入 / IME、源跟踪等通过 `GetRealForegroundWindow()` 读取 Windows 真实状态。FG 禁用覆盖后，源游戏正常取得前台，呈现侧再次看到不同进程的前台身份。现有日志在该时刻明确记录 `sourceForeground=true`，应先修复此呈现侧断开。

**点击源画面的行为保留，修正呈现资格、返回覆盖和前台分类的一致性。** 排查点击前后是否存在短暂的身份分类变化、参数焦点交接或错误暂停；以事件记录定位具体分支。

### 2.4 主界面焦点说明存在同进程激活通路

`MainWindow.cpp` 的 `WM_ACTIVATE` 仅更新标题栏激活外观；主界面点击会让 `Magpie.exe` 成为真实前台进程。控制器在两个开关关闭时为 Off，因此用户看到的恢复与真实 Magpie 前台及驱动选择有关。当前优先推断是驱动消费了窗口 / 进程的前台关联；主界面重绘及 Z-order / PresentMode 的伴随变化一并记录。

Beta2 的前台分类只有 `Source / ParameterHost / Output / SourcePopup / External / None`，主界面归入 External。需要明确区分主界面与真正的外部应用，保持输入与呈现各自正确的策略。主界面在用户控制下获得焦点时，记录实际主界面身份；正常游玩时，目标呈现查询继续绑定最终输出。

**修正方向：让正常源前台条件下的呈现保持正确关联，用户无需点击主界面来恢复 VRR。** 关闭功能时撤销 Magpie 的请求与覆盖；主界面真实激活时的驱动行为作为独立对照记录。

## 3. 目标界面与配置规则

- 名称：**VRR 可变刷新率**。
- 描述：**让显示器刷新率跟随输出帧率，提升画面流畅度。**
- 位置：**配置文件 → 帧率与刷新 → 高级选项 → 重复帧检测上方**。
- 一个 ToggleSwitch，默认关闭；调整后在重新启用缩放时应用。
- 删除原独立 NVIDIA 前台兼容卡片，移入高级选项；中 / 英 / 繁体标题、描述和无障碍名称同步。
- 高级选项描述包含“可变刷新率、重复帧检测与空闲重绘”。

已以 `frameRefresh.vrrEnabled` 作为唯一公开持久化意图。旧兼容字段被忽略，旧 VRR 字段保持权威；新写入移除旧兼容字段，运行时兼容由 VRR 状态与实际输出厂商派生。

| 旧 vrrEnabled | 旧 nvidiaForegroundCompatibilityEnabled | 新统一开关 |
| --- | --- | --- |
| false | false | 关闭 |
| false | true | 关闭 |
| true | false | 开启，并派生 NVIDIA 兼容 |
| true | true | 开启，并派生 NVIDIA 兼容 |
| 缺失 / 类型损坏 | 任意 | 按现有恢复规则取默认关闭 |

旧 `vrrEnabled` 的显式意图保持权威；运行中参数面板的过期快照不能重新引入旧兼容偏好，默认、重置、复制配置和类型修复使用同一规则。
