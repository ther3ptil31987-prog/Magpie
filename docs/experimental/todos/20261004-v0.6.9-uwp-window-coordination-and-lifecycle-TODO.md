## 1. 从必要条件推导方案

缩放需要有效的源、可用的捕获、可用的渲染输出。OS 的 owner 关系用于窗口协作，并不等同于捕获授权或 Renderer 初始化。Owner 一方面提供层级和生命周期联动，另一方面可能建立跨进程同步消息等待路径；不能仅用“设置成功／失败”一个布尔值承载这几种职责。

| 必须保持的行为 | 约束与推荐实现 |
| --- | --- |
| 捕获正确内容 | 保留经过验证的捕获 HWND、裁剪和坐标计算；选取 owner 候选不得暗中更换 WGC 捕获目标 |
| 初始化、重建及关闭不传播已知死锁 | 这些阶段先切断跨进程 owner 关系，再进入可能等待后端、驱动锁或 SDK 的步骤；保留 NGX 故障隔离和停止后的回调保护 |
| 缩放结果按原设计显示 | 正常 Win32 路径保留原生 owner。拒绝关联的路径必须显式维护输出相对源、弹窗及其他前台窗口的顺序 |
| 输入和焦点正确 | 维持 `WS_EX_NOACTIVATE`、既有鼠标／键盘转发、参数输入窗口和触控逻辑；建立 owner 与解除输入队列关联分别管理 |
| 源最小化、隐藏或退出时输出正确退场 | 原生 owner 可以提供部分 OS 联动；无 owner 模式须有独立于新画面到来的源状态通知和会话失效处理 |
| 故障能定位 | 分别报告捕获、窗口协作、Renderer 和 SDK 阶段；只有满足兼容模式条件的关联拒绝才允许继续 |

微软文档说明 owner 会维持相对层级，并在 owner 最小化／销毁时隐藏／销毁关联输出；这些功能必须在兼容路径中有对应实现。见 [Owned Windows](https://learn.microsoft.com/en-us/windows/win32/winmsg/window-features#owned-windows)。此处推荐的是功能和等待边界的分离，不承诺绕过操作系统拒绝 owner 的限制。

## 2. 方案审查时确认的源码缺口

1. [ScalingWindowOwner.h](../../../src/Magpie.Core/include/ScalingWindowOwner.h) 当前将“有效窗口、请求非空、实际 owner 为空”统一归为 `Rejected`，不检查原始错误属于能力拒绝还是其他故障。后续应收紧准入，并要求兼容控制器先准备完成。
2. [ScalingWindow.cpp](../../../src/Magpie.Core/ScalingWindow.cpp) 的 `_UpdateFocusStateAsync` 将主要层级更新放在 `oldTopmost != newTopmost` 内。原生 owner 的自动层级约束缺失后，置顶标志不变仍可能需要重新安排层级；现有实现没有独立表达这个要求。
3. `_CalcTopmostState` 和 [ScalingService.cpp](../../../src/Magpie/ScalingService.cpp) 的 `IsPopupWindow` 将 `GW_ENABLEDPOPUP` 的空／非空直接用于弹窗判定。微软文档规定没有可用 owned popup 时可返回窗口自身；自身必须与真正弹窗区分。是否已经导致某一实机症状尚未确认，需针对性测试。见 [GetWindow](https://learn.microsoft.com/en-us/windows/win32/api/winuser/nf-winuser-getwindow)。
4. `ScalingWindow::Destroy` 和 `_MessageHandler` 的 `WM_DESTROY` 前置处理都会在 case 内解除 owner 之前调用 `Renderer::BeginShutdown`。该函数实际调用 `_reflex.Stop()`；[ReflexController.h](../../../src/Magpie.Core/ReflexController.h) 的 `Stop` 获取配置互斥锁并调用驱动配置，并非纯粹发布停止标记。这说明完整停止入口在解除前存在等待点，尚未通过持锁故障注入验证其影响。
5. [现有测试提取器](../../../scripts/tests/test_scaling_window_owner.py) 只检查 `case WM_DESTROY` 内的顺序，没有检查上述 `Destroy` 和消息处理前置入口。因此已通过的局部顺序测试不能证明完整停止流程安全。
6. 若真实 owner 解除失败且关联仍在，当前 case 只写警告，随后仍 `_renderer.reset()`；[Renderer.cpp](../../../src/Magpie.Core/Renderer.cpp) 析构会 join 后端并关闭 NGX。该异常路径仍缺少在进入阻塞清理前切断关系的兜底。

这些缺口记录基于阶段 1，已由本轮实现补齐。第 4、6 项来自当时调用链审查，不是已复现的新 UWP 死锁。第 2、3 项也不能在无实测时当作 Issue 65 的已确认根因。

## 3. 推荐窗口协作模式

显式记录每个会话的 `captureHwnd`、用于焦点／显示联动的 `sourceRootHwnd`、输出 HWND、源 PID／TID、会话代次和窗口协作模式。当前多数场景的两个源 HWND 可以相同；只有实际窗口结构证明不同，才引入独立映射。

| 模式 | 进入条件 | 运行行为 |
| --- | --- | --- |
| `NativeOwned` | 初始化完成，目标顶级窗口经过校验，实际 owner 回读为请求的候选 | 保留原生 owner 与原有正常窗口行为；仅在实际关联后执行原输入队列解除逻辑 |
| `ManagedUnowned` | 目标和输出有效、捕获初始化有效、兼容控制器就绪；原始错误属于已确认的关联能力拒绝，实际无 owner | 保留源会话绑定，以程序显式维护层级、焦点规则、最小化／关闭响应；没有建立原生 owner，不做对应输入队列解除 |
| 失败 | 目标失效／被替换、输出不是本会话顶级窗口、意外 owner、权限检查失败、无法分类的 API 错误，或控制器准备失败 | 继续使用对应真实错误路径；不能为了启动成功一律放行 |

先检查原源窗口或其经过验证的 `GA_ROOT` 顶级祖先是否是正确关联目标。`GA_ROOTOWNER` 会继续沿 owner 链向上走，不能直接替代目标，否则可能关联到别的窗口。映射变化不得同时改变捕获目标、裁剪或应用选择。见 [GetAncestor](https://learn.microsoft.com/en-us/windows/win32/api/winuser/nf-winuser-getancestor)。附件中的 `ApplicationFrameWindow` 已是框架窗口且被拒绝，因此不能假定换成顶级窗口就必然解决 Issue 67。

以错误 87 的本次证据作为首个兼容案例，结合目标结构、实际关系和既有完整性级别检查判断。窗口类用于诊断和回归覆盖，不作为唯一开关；错误 5 必须核对权限语义，1400 必须核对失效竞态，未知错误保留技术诊断并停止。不要使用管理员重试、`SetParent`、桌面／任务栏 owner 或代理 owner 来强行绕过本项问题。

## 4. 生命周期与停止边界

推荐启动顺序：**无 owner 创建 → 捕获／Renderer 初始化 → 首帧有效且当前会话仍有效 → 确定窗口协作模式 → 显示并报告启动成功**。原生 owner 推迟到首帧准备完成后建立，可以使初始化及首次等待都保持无关联；正常运行仍恢复既有 owner 功能。若关联步骤移到现有 `Start` 返回之后，需要同步设计该阶段的错误报告与清理，不能遗漏或重复报告。

推荐停止顺序：**发布纯停止意图并禁止新同步呈现请求 → 确认解除跨进程 owner → 清理 Reflex／输入等可能等待的对象 → 等待后端退出 → 关闭 SDK并保留最终参数快照 → 会话退役**。这里的“纯停止意图”只允许原子状态和事件唤醒；不能隐藏获取驱动互斥锁、SDK 调用或 join。

Owner 解除失败时，首选研究将窗口销毁回调与阻塞资源清理分离：回调内只发布取消、完成必要的本地输入收尾并保留资源；待本线程 `DestroyWindow` 完成、保存的旧输出 HWND 已确认销毁后，再执行保留会话资源的清理。该实现必须先证明捕获、swap chain、GPU、光标、触控及参数快照在窗口销毁到后端退出之间仍有效。当前 `WindowBaseT` 在 `WM_DESTROY` 中清空 `Handle()`，仅看到 `Handle()==nullptr` 不足以证明 `DestroyWindow` 已返回或内核窗口已不存在。

本轮已实现该兜底并验证 CPU／窗口生命周期边界，真实 GPU／呈现资源仍待产品验收。资源生命周期未证实时不能把“警告后继续 join”标成安全；也不能用强制解锁、杀后端、detach 线程或提前释放其资源绕过等待。保留正常运行中的同步呈现机制，本项验收针对已知初始化、重建和关闭等待路径，不宣称消除所有运行期 GPU／驱动阻塞。
